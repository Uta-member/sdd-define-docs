# テスト妥当性ゲート（P0-1）

[[009_フローレビュー]] の **P0-1** を詰めるための壁打ち。結論を出したら [[正式ドキュメント/SDD全体フロー]] とプラグイン（skills/agents/scripts）に反映する。

## 問題の再確認

Model B（[[007_ドキュメント管理方針]]）は「living統合テストが振る舞いを本当にカバーしていること」に全体重を乗せている。007 自身が「唯一かつ最大の条件」と明言している。にもかかわらず、現在のフローで検査しているのはテストの**存在**だけで、**妥当性**を見るゲートが一つも無い。

- `check-traceability.sh`：`.feature` の `@AC` タグを参照するテストが在るかしか見ない。`test_AC_checkout_3` の中身が `assert True` でも「カバー済み」に見える。
- 人間ゲートは req（重点）・design（軽め）のみ。**実装後の実テストを人間が見るゲートが無い。**
- `sdd-gate-reviewer` / design skill が見るのは「AC→テストの対応**方針**」であって実テストではない。

つまり回帰網は「本数」でしか担保されておらず、「中身」は誰も見ていない。生命線が実は無防備。

## 「妥当」とは何を指すか（ゲートの検査対象を定義する）

主観で「良いテストか」を悩むと [[003_手戻りポリシー]] のWhat/How判定と同じ罠にはまる。検査対象を具体的な失敗モードに落とす。狙うのは次の4つ。

1. **空虚なテスト（tautology）**：意味のあるアサーションが無い。`assert True`、生成しただけで実行結果を検証していない、例外が飛ばないことだけ見て結果を見ていない。
2. **期待値が実装由来（curve-fitting）**：最も危険。AIが同一パスで「実装」と「テスト」を書くため、テストの期待値がコードの出力に合わせて後付けされ得る。「実装のバグをテストが正としてしまう」（[[001_アイデア発散]] で自分が挙げていたリスクそのもの）。
3. **シナリオ網羅の穴**：Scenario Outline の Examples 表の一部の行しかテスト化されていない。境界値・異常系が `.feature` にあるのにテストに落ちていない。
4. **弱いアサーション**：ACが特定の結果（金額・状態遷移・副作用）を要求しているのに、ステータスコードや「例外なし」しか見ていない。

## 核心：オラクル問題と、それを解く唯一の参照点

2 の curve-fitting は「テストが正しいと誰が保証するのか（who watches the watchmen）」というオラクル問題。テストがどれだけ形として立派でも、期待値そのものが実装の出力を写しただけなら回帰網は無意味。

これを解ける参照点は一つしかない：**`.feature`（人間が承認済みの What）**。したがってゲートの本質は次の一問に収束する。

> **各テストの期待値は、`.feature` のACシナリオ（人間承認済みの契約）から導かれているか。実装の実際の出力から逆算されていないか。**

これは [[003_手戻りポリシー]] が What/How を「受入テストが変わるか？」という観測可能な問いに変換したのと同じ発想。「良いテストか？」を「期待値の出所は spec か impl か？」に変換する。

## 自動化できる範囲とできない範囲

| 失敗モード | 機械/ヒューリスティック | 人間 |
|---|---|---|
| 1 空虚 | ◎ アサーションの有無・自明passは静的に検出しやすい | 補助 |
| 3 網羅の穴 | ○ Examples 行数とパラメータ化テストのケース数を突合できる | 補助 |
| 4 弱いアサーション | △ 「何を assert しているか」の意味理解が要る（LLMエージェント向き） | 要 |
| 2 期待値の出所 | △ 静的には原理的に判定不能。LLMが `.feature` とテストを読んで「期待値がACの記述と一致するか」を照合できる | **要（最終防衛線）** |

結論：**軽量エージェント（`.feature`＋テストコードを読むだけ、実行しない）による発見的検査＋人間のスポットチェック**の二段。重い mutation testing は既定にしない（オプション扱い、後述）。

## 設計案（結論）

[[009_フローレビュー]] の対応案のうち「実装後にテスト妥当性を見る軽ゲートを追加」を採る。位置は **implement 完了後 / accept のエビデンス凍結前**。

### 1. セルフチェック・エージェント（`sdd-test-reviewer` を新設）

- `sdd-gate-reviewer`（req/design のスナップショット検査）とは分ける。あちらは「方針」を、こちらは「実テストコード」を見る——検査対象が別物なので役割を混ぜない。
- 入力：この作業単位の `.feature` と、対応する実テストコード（**実行しない。読むだけ**）。
- チェックリスト：
  1. 各 `@AC` タグ付きシナリオに対応するテストで、意味のあるアサーションがあるか（空虚検出）。
  2. **期待値が `.feature` のシナリオの Then 節と対応しているか**（curve-fitting検出、最重要）。実装ファイルを読まずに `.feature` だけで期待値の妥当性を判断できるか、を基準にする。
  3. Scenario Outline の Examples 全行がパラメータ化テストのケースに現れているか。
  4. ACが具体的結果を要求する箇所で、アサーションがその結果を検証しているか（弱いアサーション検出）。
- 出力：`sdd-gate-reviewer` と同じく `[重要度] <AC-ID/ファイル> — 指摘と修正案` の一覧。**「これは人間ゲートの代替ではない」を明記。**

### 2. 人間ゲート（軽め）

- エージェントの指摘 ＋ 「妥当性の要点」を短く提示して停止し、人間が確認。
- 目的は curve-fitting とオラクル汚染の早期検知。全テストの精読は求めず、**エージェントが疑わしいと挙げたテストと、AC単位で1〜2件のスポットチェック**に絞る。
- design ゲート（軽め）と同格の負荷に抑える。

### 3. ブロック性

- **この妥当性ゲートはブロックする**（trace の非ブロックとは別扱い）。生命線なので、ここだけは通過を必須にする。[[009_フローレビュー]] P2-2（生命線を守る仕組みが一つもハード強制されていない）への回答も兼ねる。

### オプション（既定にしない）

- **mutation testing**：coverage の質を機械で測れる最右翼だが、実行コスト・CI整備が重い。プロジェクト成熟度に応じて任意採用とし、既定フローには入れない（軽ゲート原則を優先）。

## 論点として保留（このゲートの外）

- **NFR-AC**（[[009_フローレビュー]] P1-2）：p95・可用性等は統合テスト回帰網に乗らない。妥当性ゲートの対象外とし、監視/負荷試験側で担保する区分を別途規定（P1-2で扱う）。
- **check-traceability.sh の強化**：中身の妥当性まではスクリプトで見ない方針を維持（静的には原理的に無理）。スクリプトは「存在」担当、妥当性は本ゲート担当、と役割を分ける。
