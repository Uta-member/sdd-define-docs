# 保守開発とSDD

## 出発点：001の「保守はSDDと相性が悪い」という懸念

001では保守開発について「仕様駆動との相性が悪い」「初版リリース後は仕様駆動しないほうがいいのかも？」とされ、見通しが立っていなかった。

## 大前提の転換：007のモデルでは「すべての開発がすでに差分開発」

[[007_ドキュメント管理方針]] で「要件・設計は作業単位の差分（追記ログ）、現在の真実はコード＋テスト」と決めた。ここから重要な帰結が出る。

**新規開発の5個目の作業単位は、既に「既存システムへの変更」をしている。** Phase 0を終えて最初の数機能ができた時点で、既に「保守スタイル」の作業をしている。「新規開発の途中の1作業」と「リリース半年後の保守1件」に本質的な差はない。

→ **保守は別モードではなく、SDDサイクルの定常状態そのもの。** 001の「相性が悪い」「初版後はSDDしないほうがいい」は、SDD生まれのシステムに関してはむしろ逆。

## 本当の分岐は「新規 vs 保守」ではなく「SDD生まれ vs レガシー」

### Case A：SDD生まれのシステムの保守
- living な真実（AC-ID付きのコード＋ユニット/統合テスト）が存在し、信頼できる。
- 保守1件は**普通の作業単位と完全に同一**：影響するAC-IDをgrepで洗い出す（[[004_トレーサビリティ]]）→ 要件・設計の差分スナップショット作成 → .featureを新規AC-IDで追加/supersede（007）→ livingテスト更新 → 実装 → 実行。
- **回帰の安全網（007の絶対条件）こそが保守を安全にする。** 変更してもテストが破壊を検知する。
- 結論：「相性が悪い」は当てはまらない。むしろSDDを続けることが安全と速度の源泉。**v1後こそSDDの本領。**

### Case B：レガシー（非SDD）システムの保守
- AC-IDなし、テストが無い/貧弱、要件・設計の履歴なし。**安全網が無い。**
- ここでは001の直感（「AIで周辺ソースを洗い出し、破壊しないよう修正」）が正しい。網が無いから。
- ただし答えは「SDDを諦める」ではなく「**触る所から段階的にSDDへブートストラップ**」：
  - 変更する箇所に、まず**現状の振る舞いを固定するテスト（characterization test）**を書き、AC-IDを振る → その安全網の下で変更する。
  - 全面リバースエンジニアリング（既存の作り直しフロー）を最初にやる必要はない。**触った所だけ網が育つ**（stranglerパターン）。時間とともにCase Aへ収束する。

## 保守の変更タイプは、全部すでに作った道具に載る（新しい方法論は不要）

| 変更タイプ | 扱い | 使う道具 |
|---|---|---|
| 機能追加 | 新規ACを採番、普通のサイクル | 007 |
| 振る舞い変更 | ACをsupersede（Whatの誤り相当） | [[003_手戻りポリシー]] / 007 |
| リファクタ | AC不変、livingテスト網に全依存（How-only） | 003 |
| バグ修正 | 再現するテストを足して赤→修正で緑。＝テストの穴を埋める行為 | 003 / 007 |

保守は新しい仕組みを何も必要とせず、**003・004・007の帰結として落ちてくる。** 唯一新規なのはCase Bのブートストラップ戦略だけ。

## 「軽量SDDサイクル？」への答え

別立ての軽量サイクルは要らない。**普通のサイクルが変更規模に応じて自然にスケールダウンする**だけ（小さな変更ではイベントストーミングを省く等）。保守が省くのは一度きりのPhase 0のみ。これは小さな新規作業単位でも同じ。

## 001の結論の修正

- 保守はSDDの**対象内**。
- 「相性が悪い」のは**レガシー（テスト網なし）に限った話**で、その答えも「諦める」ではなく「触る所から網を育てる（characterization test）」。

## まとめ

**保守＝SDDの定常状態。分岐はSDD生まれ（＝普通の作業単位）かレガシー（＝触る所からブートストラップ）かだけ。**
