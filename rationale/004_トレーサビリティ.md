# トレーサビリティ（追跡可能性）

## 基本方針：特定ツールに依存しない

最重要の制約は「**特定製品（Obsidian / Git）に依存しない**」こと。理由は2つ。

1. ツール利用を**強制できない**。
2. 特定ツールへの依存自体が怖い（環境が変わると破綻する）。

ここで「特定製品への依存」と「普遍的な能力（テキスト検索）への依存」を区別する。前者は避けるが、後者はどんな環境にも存在するので依存してよい。

## 唯一の土台：プレーンテキストのID文字列

追跡の土台を、たった1つに絞る：**`REQ-checkout-1` のようなプレーンテキストのID文字列**。

- grep / VS Code検索 / Ctrl-F / `Select-String` など、どんなテキスト検索でも見つかる。特定ツールに依存しない。
- Obsidianのwikilink機構も、gitのコミット履歴も、CIも**一切使わない**。IDはすべて成果物ファイルの本文そのものに書く。

## リンクの向き：下流が上流を「自分の本文に」宣言する

バックリンク生成（Obsidian）やgit blameに頼れないので、リンクは全部ファイル本文に明示的に書く。二重管理を避けるため、正とする向きは1つ。

> **下流の成果物が、自分が満たす上流IDを自分のヘッダに宣言する。逆方向（上流→下流）は「そのIDで全文検索する」ことで得る。**

検索はどんなツールでもできるので、逆引き用の台帳を維持する必要がない。

## IDの背骨（2段）

既存の2成果物に素直に対応させる。

IDは**名前空間付き**：`<PREFIX>-<slug>-<n>`（`<slug>`＝作業単位の一意な短い英語名、`<n>`＝unitローカル連番）。並行ブランチでの採番衝突を構造的に防ぐ（下の「採番は名前空間付き」節）。

- `REQ-<slug>-<n>`：要件（利用者視点の能力）＝要件定義書
- `AC-<slug>-<n>`：受入基準（テスト可能な単位、REQに属する）＝受入テスト一覧 ← **実質の背骨**
- `NFR-<slug>-<n>`：測定可能な非機能要件（性能・可用性・セキュリティ等）。機能ACと**検証トラックが別**（回帰網でなく負荷試験/監視/診断）なので採番を分ける。Phase 0 の全体NFRは `NFR-arch-<n>`（→ [[011_NFR検証ライフサイクル]]）
- `ADR-<slug>-<n>`：設計判断（Why）。Phase 0 由来は `ADR-arch-<n>`

## IDをどこに書くか

タスクは廃棄可能であり、git履歴も橋にしないので、**永続するコード側のリンクはコード自身とテストが担う**。

| 場所 | 書くID | 形式（例） | 永続性 |
|---|---|---|---|
| 要件定義書 | `REQ` を定義 | 見出しに `## REQ-checkout-1 決済処理` | 永続 |
| 受入テスト一覧（.feature） | 各シナリオに`@AC`/`@REQ`タグ | `@REQ-checkout-1 @AC-checkout-3` + `Scenario: ...`（[[005_受入テストのフォーマット]]） | 永続 |
| 詳細設計書 | 各節に`REQ`/`AC` | `## 決済サービス [REQ-checkout-1, AC-checkout-3]` | 永続 |
| ADR | ヘッダに関連`REQ` | `ADR-checkout-1 / 関連: REQ-checkout-1` | 永続 |
| テストコード | `AC` を名前/コメント | `test_AC_checkout_3_card_payment_succeeds` | 永続（コード） |
| ソース（ファイル頭） | 実装する`REQ`/`AC`を粗く | 先頭コメント `implements: REQ-checkout-1, AC-checkout-3` | 永続（コード） |
| ソース（判断箇所） | `ADR` のみ | `// ADR-checkout-1: 冪等キーで二重決済防止` | 永続（コード） |
| 実装タスク（廃棄可能） | 上流を自由に参照 | 作業中の利便のみ | 廃棄可 |

**テストが最強の橋**。SDDではテストがACを検証し、かつコード内に住むので、`AC-checkout-3`をテスト名に入れるだけで「AC→テスト→対象コード」の永続リンクが自然に手に入る（どうせテストは書く）。だからソース側の注釈は軽く（ファイル単位の粗い宣言＋判断箇所のADRのみ）で済む。

- ソースコメントに要件IDをベタベタ書かない（ノイズ＆腐敗の元）。行単位のコメントは`ADR`だけに絞る。

## 逆引き・前方追跡の実際（ツール非依存）

- **後方（このコードはなぜ存在するか）**：コード先頭の `implements: REQ-checkout-1` を読む → 要件定義書へ。判断理由は近くの `// ADR-checkout-1` → ADRへ。
- **前方（この要件を変えたら何が壊れるか）**：文字列 `REQ-checkout-1` をリポジトリ全体（md＋コード）に全文検索。宣言した全成果物がヒットする。手戻りポリシーの影響分析（[[003_手戻りポリシー]]）に直結。

## 「現在有効なAC」は検索だけでは求まらない（supersedeの帰結）

supersede（[[007_ドキュメント管理方針]]）を導入した結果、`grep REQ-checkout-1` や `grep AC-checkout-3` は**生きたACと廃止済みACを混在で返す**。要件定義書や `.feature` は作成時点のスナップショット（追記型）なので、旧AC-IDもファイル本文に残り続け、全文検索は両方をヒットさせる。「前方追跡は全文検索一発」は、生死の区別まではしてくれない。

導出ルールを1つ明文化する：

> **現在有効なAC ＝ living統合テスト網が現在参照しているAC-ID。**

- 根拠：背骨の「現在の真実はソース＋テストだけ」「livingテストは常に最新IDを担ぐ（supersede時にIDを張り替える）」から必然的に導かれる。廃止されたACはテスト網から外れ、最新ACだけがテスト網に載る。
- 実際の求め方：テストコードを `test_AC_` で全文検索して集めたAC-IDが「今生きている集合」。要件/.featureのgrep結果は「そのIDが過去に登場した全履歴」であり、そこからテスト網に載っていないものを引くと廃止済みが分かる。
- 前方影響分析（このコードを変えたら何が壊れるか）では、grepで候補を広く集めてから、テスト網が担ぐIDで生きている範囲を確定する、という2段で読む。
- 例外：NFRは `NFR-<slug>-<n>` で別採番し回帰網に載せない。この導出ルールの対象外（別ライフサイクルで担保。→ [[011_NFR検証ライフサイクル]]）。

## 採番は名前空間付き（並行ブランチの衝突対策）

フラット連番を全文検索の max+1 で採ると、並行ブランチが同時に同じ番号を採り、マージ後 `grep AC-013` が無関係な2件を返す。しかもこの衝突は**意味的**で git のテキスト競合にならないため、GitLab等のサーバ側直接マージで**沈黙して混入する**（[[012_採番の衝突と直列化]]）。

対策は**IDに作業単位のslugを名前空間として含める**こと：

> **ID＝`<PREFIX>-<slug>-<n>`（例 `AC-checkout-3`）。`<slug>` は作業単位の一意な短い英語名、`<n>` はunitローカルの連番（1始まり）。グローバル一意性は「slugの一意性」に還元される。**

- slug一意性は**構造的に**担保される：作業単位ディレクトリを `units/<slug>/` とすると、同slugの2ブランチは同一パス `units/<slug>/requirements.md` を作り、git の add/add 競合になる。ローカルpull無しのGitLab直接マージでも「conflict」で必ず止まり、**声を上げて**露見する。別slugなら別パス＝IDも別。
- 結果、**強制もCIもマージ時の振り直しも不要**。IDは誕生時に確定し二度と動かない。採番は unit内でローカルに 1,2,3… と振るだけで、repo全体の max+1 grep は要らない。
- slug は小文字英数字のみ・ハイフン無し（区切りと衝突しないため）。Phase 0 の全体NFR/ADRは固定名前空間 `arch`（`NFR-arch-<n>` / `ADR-arch-<n>`）。

## 台帳（トレーサビリティ・マトリクス）は「あってもいいが正ではない」

一覧表が欲しければ作ってよいが、それは**検索で再生成できるキャッシュ**であって正本ではない。台帳が古くなっても、真実は各ファイル内のIDにあり、いつでも検索で作り直せる。→ どのツールにも、どの台帳にも依存しない。壊れて困るものが無い状態。

## 「強制できない」問題への答え：破綻ではなく劣化

強制できないからこそ、この方式が向いている。

- プレーンテキストIDは**優雅に劣化する**：リンクを書き忘れても、検索でヒットしないだけで、何も壊れない・誤誘導しない。（手動マトリクスは古くなると積極的に嘘をつくので最悪）
- 記入の規律は人間ではなく**AIに寄せる**：各生成ステップの出力ルールに「対応IDをヘッダに書く」を組み込む。人間の強制力に依存しない。
- 任意で**発見的チェック**：「IDのないACやコミットを報告する」スクリプト/AIレビューを回してもよいが、これはブロックしない補助であり、必須ではない。

## まとめ

土台はプレーンテキストIDと全文検索だけ。Obsidian・Git・CIはすべて任意の便利機能であり、無くても追跡が成立する。
