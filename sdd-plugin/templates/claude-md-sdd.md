# SDD（仕様駆動開発）ルール

このプロジェクトは SDD で開発する。作業は必ず sdd プラグインのスキルに従って進める：
`/sdd:req` →（人間レビュー・重点）→ `/sdd:design` →（人間レビュー・軽め）→ `/sdd:tasks` → `/sdd:implement` →（テスト妥当性ゲート・軽め/ブロック）→ `/sdd:accept`

## 背骨（常に守る4原則）

1. **現在のシステムの真実は「ソース＋ユニットテスト＋統合テスト」だけ**（＋例外として {DOCS_DIR}/architecture.md）。要件定義・詳細設計・.feature・受入結果は作業単位ごとの差分スナップショット（write-once）であり、最新の全体状態を表さない。
2. **作業単位は小さく**：1つの小さな機能 = 1ブランチ = 1 PR。手戻りしてもAI実装が数時間で終わる規模に切る。要件・設計・.feature・テスト・コード・ADRは同じPRに全部入れる（atomic co-change）。
3. **追跡はプレーンテキストID（`REQ-<n>` / `AC-<n>` / `ADR-<n>`）と全文検索だけ**。台帳・マトリクスは検索で再生成できるキャッシュであり正本ではない。Obsidian・Git・CIの固有機能に依存しない。
4. **受入レベルの振る舞いは必ずliving統合テストに吸収する**。回帰の安全網（ユニット/統合テスト）を常に高精度に保つことが全体の前提条件。

## ID規約

- **採番**：リポジトリ全体を `REQ-` / `AC-` / `NFR-` / `ADR-` で全文検索し、最大番号 + 1 を使う。
- **NFR（測定可能な非機能要件）**：`AC-` ではなく `NFR-<n>` で別採番する。機能ACの回帰網（ユニット/統合テスト）ではなく**負荷試験・本番監視/SLO・セキュリティ診断**の別トラックで担保する。目標値＋検証手段を併記。`.feature`では `@NFR-<n>` タグ。check-traceability の対象外（回帰の穴ではない）。
- **supersede**：既存の振る舞いを変えるときは旧IDを書き換えず、新IDを採番して本文に `supersedes: AC-007` のように明記する。livingテストは常に最新IDを担ぐ。
- **現在有効なACの導出**：`grep AC-` は要件/.featureのスナップショットに残る旧IDも返すので、生死が混在する。**現在有効なAC ＝ livingテスト網（`test_AC_`）が現在参照しているAC-ID**。前方影響分析は「全文検索で候補を広く集める → テスト網が担ぐIDで生きた範囲を絞る」の2段で行う（`NFR-<n>` は回帰網外なのでこの導出の対象外）。
- **.feature**：シナリオに `@REQ-005 @AC-012` タグを付ける。step定義は書かない・Cucumber実行エンジンは使わない（.featureは構造化仕様書＋機械抽出対象）。
- **テスト**：{TEST_NAMING}
- **ソース**：ファイル先頭コメントに `implements: REQ-005, AC-012` を粗く宣言。行単位コメントは設計判断箇所の `// ADR-003: 理由` だけに絞る。要件IDを行単位でベタベタ書かない。

## ドキュメント配置とライフサイクル

| パス | 区分 | 扱い |
|---|---|---|
| ソース・ユニットテスト・統合テスト | living（真実） | HEADが真実。常に高精度に保つ |
| {DOCS_DIR}/architecture.md | living（例外・散文） | 維持する。基盤アーキ変更は多数の作業単位に波及する re-baseline |
| {DOCS_DIR}/adr/ | スナップショット | 不変。変更はsupersedeで追記 |
| {DOCS_DIR}/units/<日付-スラッグ>/ | スナップショット | requirements.md / design.md / evidence.md。**マージ後は変更禁止** |
| .feature（テストコードと同じディレクトリに置く） | スナップショット | 作成時の意図の記録。振る舞いの保証は統合テストが担う |
| {DOCS_DIR}/units/<...>/tasks.md | 廃棄可能 | 作業記憶。**マージ前に削除する** |
| {DOCS_DIR}/generated/ | キャッシュ | 現在仕様書は維持せず、必要時にコード＋テストから再生成 |

## レビューゲートと手戻り

- 要件定義の後：**人間レビュー（重点）**。承認されるまで設計に進まない。
- 詳細設計の後：**人間レビュー（軽め）**。的外れ・インフラ影響を確認。
- 実装の後：**テスト妥当性ゲート（軽め・ブロック）**。`sdd-test-reviewer` が実テストと.featureを突き合わせ、空虚なテスト・期待値の実装由来（curve-fitting）・網羅の穴を検出。テストの期待値が.feature（人間承認のWhat）由来かを人間がスポットチェック。生命線なので通過必須。accept はこの通過が前提。
- **Howの誤り**（要件は正しいが設計/コードが誤り）→ 誤った成果物まで局所ループ。受入テストは変わらない。
- **Whatの誤り**（要件・受入仕様が誤り）→ 要件定義まで戻り人間が再承認 → 下流を再導出。**これは例外ではなく正規ルート**。
- 原則その場で直しきる（コード先行を作らない）。
