# /sdd:tasks — 実装タスク作成（廃棄可能）

## 前提

- 同じ作業単位の design.md が人間レビュー（軽め）を通過済みであること。

## 手順

1. `{DOCS_DIR}/units/<作業単位>/tasks.md` に実装タスク一覧を書く。
   - 順序付きのチェックリスト形式。各タスクに関連する REQ/AC/設計節を自由に参照してよい（このファイルは廃棄可能なので参照ルールは緩い）。
   - テスト実装（ユニット・統合）もタスクに含める。
   - 状態マーカーは `[ ] 未着手` / `[~] 実行中` / `[x] 完了` の3つ。implement 中はこれを逐次更新する。
   - **末尾に「## 作業ログ」節を空で用意しておく。** implement が進捗・触ったファイル・見つかった問題・次の一手を書き足す場所で、セッションを切ったあとの唯一の引き継ぎ媒体になる。

   ```markdown
   ## タスク
   - [ ] 1. ... （REQ-x-1 / AC-x-2, design.md §3）
   - [ ] 2. ...

   ## 作業ログ
   （implement が追記。触ったファイル / 見つかった問題・判断 / 次の一手）
   ```
2. **人間レビューは求めない。** これは作業中の作業記憶であり、人間は受入テストと設計の妥当性に集中する。
3. **ここでセッションを切る。** `/clear` してから `/sdd:implement` を新しいセッションで始める。implement は機能サイクルで最もコンテキストを食う工程（コード＋テストを大量に読み書きする）なので、要件定義・設計の対話ログを背負ったまま入らない。下流が必要とするものは design.md と tasks.md に全部書いてある。

## ライフサイクル（重要）

- tasks.md は**廃棄可能**。マージ前（`/sdd:accept` の最後）に削除する。履歴復元にも依存しない。
- 作業中は自由に書き換えてよい（進捗チェック・追記・並べ替え）。むしろ**書き換え続けることが役割**：廃棄可能なのは「マージ後に価値が無い」という意味であって、作業中は最も重要な引き継ぎファイル。
- implement 中にコードだけ進んで tasks.md が古くなると Stop フック（`tasks-log-guard.sh`）が警告する。
