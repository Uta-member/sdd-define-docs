# /sdd:implement — 実装（コード＋テスト）

## 手順

tasks.md に従って実装する。以下のSDDルールに沿って進める。

### テスト（最重要）
- ユニットテスト・統合テストを実装する。
- **【不変条件】受入レベルの振る舞いは統合テストに吸収する。** .feature の各ACシナリオに対応するテストを、CLAUDE.md の規約（例：`test_AC_checkout_3_card_payment_succeeds`）で命名して書く。これが恒久的な回帰網になる。.feature 自体は実行しない（step定義を書かない）。
- Scenario Outline の Examples 表はパラメータ化テストに素直に対応させる。
- supersede したACがある場合：livingテストを**新しいAC-IDに付け替える**（旧IDのテストは新テストに置き換え）。旧IDはスナップショット内にだけ残る。

### ソースコードのID規約
- 新規/変更ファイルの先頭コメントに粗く宣言：`implements: REQ-checkout-1, AC-checkout-3`。
- 設計判断の箇所にだけ `// ADR-checkout-1: 冪等キーで二重決済防止` の形でADRコメント。**要件IDを行単位でベタベタ書かない**（ノイズ＆腐敗の元）。

### 手戻りの判定
実装中に問題を見つけたら、受入テストが変わるかどうかで遡り先を決める：
- **受入テストが変わらない（Howの誤り）**：`/sdd:design` に局所ループ。design.md を直してから実装を続ける。人間の再承認は不要（軽く報告はする）。
- **受入テストが変わる（Whatの誤り）**：作業を止めて `/sdd:req` に戻り、要件を直して**人間の再承認**を得てから下流を再導出する。
- 原則その場で直しきる。コード先行（要件と乖離したままのコード）を作らない。

### 完了条件
- tasks.md のタスクが全て完了し、全テスト（既存含む）がパスしている。
- `/sdd:trace` で乖離チェックを走らせ、テストの無いACが残っていないことを確認する（結果はブロックしない。accept時にも再度走る）。

### テスト妥当性ゲート（軽め・ブロック）
テストの**存在**はtraceで見たが、**中身**はまだ誰も見ていない。回帰網が振る舞いを本当にカバーしているかをここで検査する。trace とは違い、**このゲートはブロックする**（不変条件2を実際に守れているかを確かめる唯一の場だから）。

1. `sdd-test-reviewer` エージェントに、この作業単位の `.feature` と対応する実テストコードを検査させる（テストは実行しない・読むだけ）。狙いは空虚なテスト（`assert True` 等）・**期待値が実装由来（curve-fitting）**・シナリオ網羅の穴・弱いアサーションの検出。
2. 指摘があれば直す（テストの誤りは How の局所ループ。ただしACの解釈が揺れるなら What として `/sdd:req` へ）。
3. **人間ゲート（軽め）**：エージェントの指摘と妥当性の要点を短く提示し、疑わしいテスト＋AC単位で1〜2件のスポットチェックを人間に依頼して停止する。全テストの精読は求めない。
4. 通過したら**セッションを切って**（`/clear`）新しいセッションで `/sdd:accept` へ。実装セッションは大量のコードを読んだ後で最も重くなっている。accept が必要とするのは .feature とテストコードとコミット履歴で、いずれもファイルから読める。
