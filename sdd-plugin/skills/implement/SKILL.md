# /sdd:implement — 実装（コード＋テスト）

## 手順

tasks.md に従って実装する。以下のSDDルールを厳守する。

### テスト（最重要）
- ユニットテスト・統合テストを実装する。
- **受入レベルの振る舞いは統合テストに吸収する（絶対条件）。** .feature の各ACシナリオに対応するテストを、CLAUDE.md の規約（例：`test_AC_012_card_payment_succeeds`）で命名して書く。これが恒久的な回帰網になる。.feature 自体は実行しない（step定義を書かない）。
- Scenario Outline の Examples 表はパラメータ化テストに素直に対応させる。
- supersede したACがある場合：livingテストを**新しいAC-IDに付け替える**（旧IDのテストは新テストに置き換え）。旧IDはスナップショット内にだけ残る。

### ソースコードのID規約
- 新規/変更ファイルの先頭コメントに粗く宣言：`implements: REQ-005, AC-012`。
- 設計判断の箇所にだけ `// ADR-003: 冪等キーで二重決済防止` の形でADRコメント。**要件IDを行単位でベタベタ書かない**（ノイズ＆腐敗の元）。

### 手戻りの判定
実装中に問題を見つけたら、受入テストが変わるかどうかで遡り先を決める：
- **受入テストが変わらない（Howの誤り）**：`/sdd:design` に局所ループ。design.md を直してから実装を続ける。人間の再承認は不要（軽く報告はする）。
- **受入テストが変わる（Whatの誤り）**：作業を止めて `/sdd:req` に戻り、要件を直して**人間の再承認**を得てから下流を再導出する。
- 原則その場で直しきる。コード先行（要件と乖離したままのコード）を作らない。

### 完了条件
- tasks.md のタスクが全て完了し、全テスト（既存含む）がパスしている。
- `/sdd:trace` で乖離チェックを実行し、テストの無いACが残っていないことを確認する。
- 完了したら `/sdd:accept` へ。
