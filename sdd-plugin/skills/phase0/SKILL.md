# /sdd:phase0 — 土台づくり（プロジェクト初回のみ）

小さな機能サイクルを回す前の一度きりの工程。順序は **入口 → NFR → アーキテクチャ**（アーキはNFRを満たすために存在する）。

## 1. 入口（どちらか一方）

- **新規開発**：イベントストーミングをユーザーと対話的に実施（ドメインイベント→コマンド→集約の順に深掘り）。結果を `{DOCS_DIR}/units/<日付>-phase0/event-storming.md` に凍結スナップショットとして保存。
- **作り直し**：既存資産からリバースエンジニアリングし、現行システム仕様書を `{DOCS_DIR}/units/<日付>-phase0/current-system-spec.md` に凍結。

## 2. 全体NFR定義

- 性能・可用性・セキュリティ等の目標を**測定可能な形**で定義する（例：「p95応答 < 300ms」。「速い」は不可）。
- 測定可能なNFRは `AC-<n>` を採番して受入基準化する（採番はリポジトリ全文検索で最大番号+1）。
- `{DOCS_DIR}/units/<日付>-phase0/nfr.md` に記録（スナップショット）。

## 3. 基盤アーキテクチャ確定 + walking skeleton

- 決めること：技術スタック／レイヤ・モジュール境界／横断的関心事（認証・エラー処理・ログ・トランザクション・API規約）。
- 成果物：
  - `{DOCS_DIR}/architecture.md` — **living**。以後維持する唯一の散文ドキュメント。簡潔に保つ。
  - 基盤ADR群 — `{DOCS_DIR}/adr/ADR-<n>-<slug>.md`。主要な技術選定・境界の判断を1件1ファイルで（不変・supersedeで追記）。
  - **walking skeleton** — 全レイヤを最小限貫通する動くコード＋テスト（CI/デプロイ経路も含めて一度通す）。

## 注意

- 基盤アーキテクチャの変更は多数の作業単位に波及する **re-baseline**。ここで決めることは人間の承認を必ず取る。
- 完了したら `/sdd:req` で最初の作業単位へ。
