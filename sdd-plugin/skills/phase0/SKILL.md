# /sdd:phase0 — 土台づくり（プロジェクト初回のみ）

小さな機能サイクルを回す前の一度きりの工程。順序は **入口 → NFR → アーキテクチャ**（アーキはNFRを満たすために存在する）。

## 1. 入口（どちらか一方）

- 作業単位ディレクトリは `{DOCS_DIR}/units/<YYYYMMDD-HHMM>-phase0/`（実施時点の日時接頭辞。→ req skill「作業単位ディレクトリ作成」節と同じ命名規約）。
- **新規開発**：イベントストーミングをユーザーと対話的に実施（ドメインイベント→コマンド→集約の順に深掘り）。結果を `{DOCS_DIR}/units/<開始日時>-phase0/event-storming.md` に凍結スナップショットとして保存（実施日は各ファイル冒頭に記録）。
- **作り直し**：既存資産からリバースエンジニアリングし、現行システム仕様書を `{DOCS_DIR}/units/<開始日時>-phase0/current-system-spec.md` に凍結。

## 2. 全体NFR定義

- 性能・可用性・セキュリティ等の目標を**測定可能な形**で定義する（例：「p95応答 < 300ms」。「速い」は不可）。
- 測定可能なNFRは **`NFR-arch-<n>` を採番**する（Phase 0 の全体NFRは名前空間 `arch`、連番は `nfr.md` 内でローカルに1始まり。共有ファイルなので並行編集は git 競合で守られる。→ 採番の衝突と直列化）。機能ACの `AC-<slug>-<n>` とは**採番も検証トラックも分ける**：NFRは機能回帰網（ユニット/統合テスト）でなく**負荷試験・本番監視/SLO・セキュリティ診断**で担保する。目標値と検証手段を併記する（例：`NFR-arch-1 API全体レスポンス / p95<300ms / 検証: リリース前負荷試験`）。
- `{DOCS_DIR}/units/<開始日時>-phase0/nfr.md` に記録（スナップショット）。
- NFRは check-traceability（機能ACの回帰網チェック）の対象外。検証結果は受入エビデンスと同様に凍結スナップショットで残す。

## 3. 基盤アーキテクチャ確定 + walking skeleton

- 決めること：技術スタック／レイヤ・モジュール境界／横断的関心事（認証・エラー処理・ログ・トランザクション・API規約）。
- 成果物：
  - `{DOCS_DIR}/architecture.md` — **living**。以後維持する唯一の散文ドキュメント。簡潔に保つ。
  - 基盤ADR群 — `{DOCS_DIR}/adr/YYYY-MM-DD-ADR-arch-<n>-<title>.md`（IDは `ADR-arch-<n>` で日付を含めない、ファイル名の日付は時系列表示専用）。主要な技術選定・境界の判断を1件1ファイルで（Phase 0 全体は名前空間 `arch`・不変・supersedeで追記）。
  - **walking skeleton** — 全レイヤを最小限貫通する動くコード＋テスト（CI/デプロイ経路も含めて一度通す）。

## 注意

- 基盤アーキテクチャの変更は多数の作業単位に波及する **re-baseline**。ここで決めることは人間の承認を取る。
- 完了したら `/sdd:req` で最初の作業単位へ。
