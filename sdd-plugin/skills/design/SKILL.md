# /sdd:design — 詳細設計（差分スナップショット）

## 前提

- 同じ作業単位の requirements.md が**人間レビューを通過済み**であること。未承認なら停止して `/sdd:req` のゲートに戻す。

## 手順

### 1. design.md を書く
- 場所：`{DOCS_DIR}/units/<作業単位>/design.md`。
- 各節の見出しに対応する上流IDを宣言する：`## 決済サービス [REQ-checkout-1, AC-checkout-3]`（下流が上流を自分の本文に書く。逆引きは全文検索で得るのでマトリクスは作らない）。
- **局所アーキテクチャ**（この作業単位に閉じる構造：クラス/モジュール構成、データフロー、DBスキーマ変更等）はここで決める。基盤アーキテクチャ（`{DOCS_DIR}/architecture.md`）に反する・変更が必要な場合は re-baseline なので必ず人間に確認する。
- 各ACをどのテスト（ユニット/統合）で検証するかの対応方針も書く。

### 2. 設計判断（Why）をADRに記録
- 迷って選んだこと・トレードオフのある判断は `{DOCS_DIR}/adr/ADR-<unit-slug>-<n>-<title>.md` に記録（この作業単位のslugで名前空間化し、連番はunitローカルに1始まり。ファイル名にslugが入るので別unitのADRと衝突しない。→ 採番の衝突と直列化）。
- ヘッダに関連IDを書く：`ADR-checkout-1 / 関連: REQ-checkout-1`。
- ADRは不変。過去の判断を変えるときは新規ADRで `supersedes: ADR-login-1`。

### 3. 【必須】人間レビューゲート（軽め）で停止
- 設計の要点（構成・主要判断・インフラ影響の有無）を短く提示し、確認を依頼して停止する。
- 目的は「的外れ・インフラ影響」の早期検知。重厚なレビューは求めない。
- 承認後に `/sdd:tasks` へ。

## 手戻り

実装中に設計の誤り（Howの誤り＝要件は正しく受入テストは変わらない）が見つかったら、ここへ局所ループで戻って design.md を直してから実装を続ける。
