# /sdd:req — 要件定義（差分スナップショット）

## 前提

- 作業単位は**手戻りしてもAI実装が数時間で終わる規模**に切る。大きければユーザーと分割を相談する。
- 1機能 = 1ブランチ = 1 PR。まだブランチが無ければ作成する（例：`feat/<slug>`）。

## 手順

### 1. 作業単位ディレクトリ作成
`{DOCS_DIR}/units/<YYYYMMDD-HHMM>-<slug>/` を作る（slugは機能の短い英語名・**小文字英数字のみ・ハイフン無し**。日時は着手時点の実際の日時を `date +%Y%m%d-%H%M` 等で取得する。開始日は requirements.md の冒頭にも記録する）。

- **slugはID名前空間そのもの**。`REQ-<slug>-<n>` 等のIDがこのslugを担ぎ、グローバル一意性は「slugの一意性」に還元される。既存の `{DOCS_DIR}/units/` に同名slugのディレクトリが無いことを確認する（同slug・同時刻の並行作成なら同一パス競合として git がマージ時に検出するが、着手時刻が違えば別ディレクトリになり自動検出は効かない——だからこの手動確認を省かない。ただしAC-ID自体の重複はcheck-traceabilityの採番衝突チェックが内容ベースで別途検知する。→ 15 ユニットディレクトリ名の日時接頭辞）。
- **日時接頭辞はソート・実施順復元専用でありID（`<slug>`）の一部ではない**（ADRファイル名の日付接頭辞と同じ発想）。ID中のslugには日時を含めない（`REQ-<slug>-1` のまま）。実施順は `ls {DOCS_DIR}/units/` で復元できる。
- **他ユニットへ相対リンクを書くときはディレクトリ名を確認してから使う**（`ls {DOCS_DIR}/units/` 等）。日時接頭辞込みの実在パスであり、slugだけでは解決しない。

### 2. 影響範囲を調べる（3段・上から順に、必要な分だけ）

**原則：予防的な全走査をしない。** 既存ACとの競合を要件定義の時点で全部読んで防ぐ設計にはなっていない。見落としは実装時に**回帰網が赤くなって検知される**（【不変条件】2）。ここでやるのは「触る範囲の周辺を安く見る」ことだけで、**全ACの読み込みはしない**（→ 16 影響範囲調査のコスト設計）。

**第1段：索引を取る（コスト一定。ここは必ず通る）**

このSKILL.mdから見て `../../scripts/list-acs.sh` を実行する（リポジトリ内ではなくプラグインルート配下）：

```
bash "<プラグインルート>/scripts/list-acs.sh"
```

現在有効なAC（`live`）とテストの無いAC（`NOTEST`）が1行1件（AC-ID・シナリオ名・定義位置）で出る。**この段では `.feature` 本体もソースも読まない。**

- AC数が多いリポジトリでは、AC行の代わりに**名前空間（slug＝作業単位）別のサマリ**に自動で畳まれる。これは地図なので、そのまま `--path <ディレクトリ>` / `--grep <キーワード>` で触る範囲に絞り込む。**`--full` で全件を開かない**（索引を読むこと自体のコストを避けるために畳んでいる）。
- 絞り込みキーは「今回触るディレクトリ」と「機能を表す語」の2つが基本。co-location により、テストコードの置き場所がそのまま影響範囲の絞り込みキーになる。

**第2段：候補だけ精読する（数件）**

索引で当たりを付けたACについてのみ、定義元の `.feature` を読む。ここで supersede 候補（今回の変更で振る舞いが変わる既存AC）を確定させる。

**第3段：実装を確認する（第2段で判断が付かない分だけ）**

該当するテストと実装を読む。**「念のため」で広げない。**

- 第3段で読むファイルが5件を超えそうなら、**作業単位が大きすぎるサイン**。調査が膨らむこと自体が範囲過大の指標なので、分割をユーザーに相談する。
- 判断が付かないまま残った領域は、**読み進めずに手順3で「調べていない」と申告する**。人間はその領域を知っているので、ゲートで指摘してもらう方がAIが全走査するより安く正確。

### 3. requirements.md を書く
- **現状のシステムに対してどう機能を追加/改善するかの差分**として書く。全体仕様の再記述はしない。現状の振る舞いの根拠はソースとテスト（＝唯一の真実）に置く。
- 構成：
  - `## 調査範囲` — 手順2の結果。冒頭（REQより前）に置く。
    - **調べた**：索引の絞り込み条件と、読んだ `.feature` / テスト / 実装のパス。
    - **調べていない**：意図的に見ていない領域と、その理由（「今回の変更と独立と判断」等）。
    - **supersede 候補**：置き換える既存AC（無ければ「無し」と書く）。
    - この節は人間レビューゲートの審査項目である。「AIが見落としていそうな領域」を人間が指摘できるようにするために書く。空欄や「全体を確認」のような実質のない記述にしない。
  - `## REQ-<slug>-<n> <タイトル>` — 利用者視点の能力。採番は**このunit内でローカルに** `1, 2, 3…` と振る（`<slug>` が名前空間なのでrepo全体のmax+1検索は不要）。
  - 各REQ配下に受入基準 `AC-<slug>-<n>`（検証可能な単位・同様にunitローカル採番）。
  - 機能固有NFRも**測定可能な形**で書き、`NFR-<slug>-<n>` を採番する（`AC-<slug>-<n>` とは分ける）。目標値と検証手段（負荷試験/監視/診断）を併記する。NFRは機能回帰網でなく別トラックで担保し、check-traceabilityの対象外（→ NFR検証ライフサイクル）。
  - 既存の振る舞いを変える場合：旧IDは書き換えず新IDを採番し、`supersedes: AC-login-2` のように明記。**supersede した旧IDを担ぐテストは実装時に新IDへ張り替える**（living テストは常に最新IDを担ぐ）。

### 4. .feature を書く
- 置き場所：**そのACを検証するテストコードを置く予定のディレクトリ**（co-location）。
- 各シナリオに `@REQ-<slug>-<n> @AC-<slug>-<n>` タグ（NFRの測定シナリオは `@REQ-<slug>-<n> @NFR-<slug>-<n>`）。Scenario Outline / Examples 表はパラメータ化テストに落とせる形で。
- **step定義は書かない。Cucumber実行エンジンには載せない。** .featureは構造化仕様書＋機械抽出対象であり、実テストは普通のテストコードで書く。

### 5. レガシー箇所に触れる場合
回帰網の無い既存コードに触れる作業単位では、**先に現状の振る舞いを固定する characterization test を要件化**する（現状の振る舞いにAC採番）。その網の下で変更する（stranglerパターン）。

- 手順2の索引で `NOTEST` が並ぶ領域＝**回帰網が薄い領域**。ここに触れる場合は「見落としはテストが検知する」という前提が働かないので、characterization test を先に置いて網を作ってから変更する。

### 6. 【不変条件】人間レビューゲート（重点）で停止
- requirements.md と .feature の要約・ACの一覧を提示し、**人間のレビューを依頼して停止する**。
- あわせて `## 調査範囲` の「調べていない」を明示的に読み上げる。人間が補える最大の情報がここにある。
- SDDで人間が最も重く見るゲートはここ。**承認されるまで `/sdd:design` に進まない。**
- レビュー前のセルフチェックとして sdd-gate-reviewer エージェントを使ってもよい（人間ゲートの代替にはならない）。
- **承認されたらセッションを切る**（→ 各スキル末尾「セッション境界」節）。requirements.md と .feature が引き継ぎ媒体なので、要件定義の対話ログを design に持ち越す必要はない。

## セッション境界

人間ゲートはコンテキストを捨てても安全な地点である。承認後に `/clear` してから `/sdd:design` を新しいセッションで始めること。下流が必要とする情報は全てファイル（requirements.md、.feature）に凍結済みで、会話履歴からしか復元できないものは無い。

長いセッションはキャッシュが効いていても高くつく。ゲートごとに切ると、機能サイクル全体のトークン消費が大きく下がる。

## 手戻り

このゲート通過後に要件の誤り（Whatの誤り＝受入テストが変わる誤り）が見つかったら、ここへ戻って修正し**再承認**を受ける。これは例外ではなく正規ルート。
