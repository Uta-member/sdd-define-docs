# /sdd:req — 要件定義（差分スナップショット）

## 前提

- 作業単位は**手戻りしてもAI実装が数時間で終わる規模**に切る。大きければユーザーと分割を相談する。
- 1機能 = 1ブランチ = 1 PR。まだブランチが無ければ作成する（例：`feat/<slug>`）。

## 手順

### 1. 作業単位ディレクトリ作成
`{DOCS_DIR}/units/<yyyy-mm-dd>-<slug>/` を作る（日付は今日、slugは機能の短い英語名）。

### 2. requirements.md を書く
- **現状のシステムに対してどう機能を追加/改善するかの差分**として書く。全体仕様の再記述はしない。現状把握はソースとテスト（＝唯一の真実）を読んで行う。
- 構成：
  - `## REQ-<n> <タイトル>` — 利用者視点の能力。採番はリポジトリ全体を `REQ-` で全文検索して最大番号+1。
  - 各REQ配下に受入基準 `AC-<n>`（検証可能な単位・同様に新規採番）。
  - 機能固有NFRも**測定可能な形**で書き、AC採番する。
  - 既存の振る舞いを変える場合：旧IDは書き換えず新IDを採番し、`supersedes: AC-007` と明記。

### 3. .feature を書く
- 置き場所：**そのACを検証するテストコードを置く予定のディレクトリ**（co-location）。
- 各シナリオに `@REQ-<n> @AC-<n>` タグ。Scenario Outline / Examples 表はパラメータ化テストに落とせる形で。
- **step定義は書かない。Cucumber実行エンジンには載せない。** .featureは構造化仕様書＋機械抽出対象であり、実テストは普通のテストコードで書く。

### 4. レガシー箇所に触れる場合
回帰網の無い既存コードに触れる作業単位では、**先に現状の振る舞いを固定する characterization test を要件化**する（現状の振る舞いにAC採番）。その網の下で変更する（stranglerパターン）。

### 5. 【必須】人間レビューゲート（重点）で停止
- requirements.md と .feature の要約・ACの一覧を提示し、**人間のレビューを依頼して停止する**。
- SDDで人間が最も重く見るゲートはここ。**承認されるまで `/sdd:design` に進まない。**
- レビュー前のセルフチェックとして sdd-gate-reviewer エージェントを使ってもよい（人間ゲートの代替にはならない）。

## 手戻り

このゲート通過後に要件の誤り（Whatの誤り＝受入テストが変わる誤り）が見つかったら、ここへ戻って修正し**再承認**を受ける。これは例外ではなく正規ルート。
